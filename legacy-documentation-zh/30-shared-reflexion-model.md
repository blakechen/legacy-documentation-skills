# Reflexion 模型（Reflexion Model）

## 目標

以人對系統的既有認知來檢驗回復出來的架構，並回報兩者不一致之處。

Murphy、Notkin、Sullivan，《Software Reflexion Models》，FSE 1995。

---

## 問題

本技能組中的每一個 Skill 都是由下而上的：讀程式碼、建立圖像。
由下而上的回復，無從察覺「它從來沒找到過的東西」，
也無從察覺「它找到的東西並不是這個系統的目的」。

現場一定有人知道這個系統在做什麼。
那份知識是整條管線中唯一「不依賴程式碼」的輸入，
而在此之前，管線裡沒有地方安放它。

---

## 方法

### 1. 陳述假設

由懂這個系統的人 —— 維運、業務分析師、資深開發者 ——
在閱讀回復出來的文件「之前」，寫下一張模組圖。

十到十五個模組。三十分鐘。

`docs/architecture/hypothesis-map.txt`

    module Web          前端控制器、路由、請求入口
    module Inquiry      唯讀查詢
    module Transfer     資金移動
    module Persistence  資料庫存取

    map ^com\.example\.bank\.web\.   -> Web
    map InquiryTrx$                   -> Inquiry
    map ^com\.example\.bank\.db\.     -> Persistence

    edge Web -> Inquiry
    edge Web -> Transfer
    edge Inquiry -> Persistence

映射規則是對完整型別名稱的正規表示式，依檔案順序評估，先符合者勝出。

### 2. 計算

`tools/reflexion/reflexion.sh` 把每個型別映射到模組上，
比對「預期的邊」與「factbase 中實際存在的邊」。

### 3. 讀三種結果

**Convergence（收斂）** — 預期有、實際也有。確認了認知。最不有趣的結果。

**Divergence（分歧）** — 實際有、但沒人預期。
一段沒人寫下來的關係。
不是關於這個系統的未記載事實，就是一個缺陷：
分層違規、抄捷徑、或殘留物。

**Absence（缺席）** — 預期有、但實際沒有。
不是認知錯了，就是這段關係走的是掃描看不到的路徑：
排程器、佇列、預存程序、檔案投遞。

**未映射型別** — 沒有任何規則符合。這不是中性的結果。
不是模型少了一個模組，就是這個型別不屬於模型所描述的系統。
兩者都值得知道。

---

## 規則

Reflexion 檢查應在列舉之後、規格產生之前執行。

每一筆 divergence 與每一筆 absence 都應在
`docs/architecture/reflexion-report.md` 中以下列之一解決

- 對假設圖的修正，以及修正的理由
- 記入 gap analysis 的一項發現，以及理由
- 掃描能力的明確界線，並指名它看不到的機制

未解決的 divergence 是關於這個系統的未決問題，
不是可以忽略的工具錯誤。

---

## 為什麼這能抓到抽取錯誤

假設是以「抽取器沒有的知識」寫成的。
當分析師確信存在的某個模組映射到零個型別時，
最可能的原因不是分析師錯了，
而是列舉漏掉了一整族類別。

這是本技能組中唯一能找出「管線從未去找過的東西」的檢查。

---

## 反面模式

以套件結構自動產生假設圖，並以此取代由人撰寫，是「禁止」的。

一張由程式碼推導出的圖，不可能與程式碼不一致。
拿工具去跑這樣的圖會得到一份乾淨但毫無意義的報告，
而這份乾淨的報告比沒有報告更糟，因為它會被相信。
