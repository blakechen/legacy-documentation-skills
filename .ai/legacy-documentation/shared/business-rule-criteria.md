# Business Rule Criteria

## Objective

Decide what is a business rule and what is not, before extraction begins.

---

## The Problem

`skills/business-rule-extraction` lists eleven kinds of thing to identify and
no kind of thing to reject. Applied literally to a legacy codebase it turns
every null check into a business rule and buries the twelve rules that
matter under four thousand that do not.

---

## Definition

A **domain variable** is a name the business owns:

- a column of a table reached by an enumerated DB object class
- a field read from a request, a screen, or an inbound message
- a configuration key that carries a threshold, a limit, a rate or a code
- a status, code or type value compared against a literal from the above

The derived list lives in `docs/business-rules/domain-variables.txt`,
generated by `tools/factbase/domain_variables.sh`.

A **business rule** is a condition, calculation or state transition that
reads or writes at least one domain variable.

Everything else is **technical logic**.

---

## The Test

For a candidate condition, ask one question:

> Which domain variable does this condition read or write?

If the answer names one, it is a business rule. Record the variable as part
of the evidence.

If the answer is "none", it is technical logic. It belongs in the module
document's Processing Flow, not in the business-rule document.

If the answer is "I cannot tell", record it as a rule with confidence Low
and state what evidence is missing. Do not silently drop it.

---

## Always Technical Logic

Unless it reads a domain variable:

- null and empty-string checks
- try / catch / finally and exception rethrows
- logging, tracing, timing
- connection, transaction and resource handling
- collection iteration bounds and index arithmetic
- string formatting, trimming, encoding conversion
- framework lifecycle calls
- defensive re-checks of a condition already checked upstream

Recording these as business rules is a defect, not thoroughness.

---

## Always a Business Rule

Even when it looks technical:

- a length or format check on a domain input field
  (`ACCTNO` must be 12 characters is a rule about accounts)
- a comparison against a configured threshold
- a code-to-behaviour mapping table
- an authorisation check keyed on a domain role or branch
- a rounding, scaling or currency-conversion calculation
- a state transition on a status column

---

## Slicing

For each transaction unit:

1. Take the domain variables the unit touches, from the derived list filtered
   by the unit's file.

2. For each one, follow it backwards through the method: which assignments,
   parameters and conditions determine its value, and forwards: which
   branches and writes depend on it.

3. The conditions on that path are the unit's business rules. Conditions off
   it are technical logic.

This is manual backward and forward slicing. It is not automated by this
library, and the result SHALL cite the lines it followed.

---

## Evidence

Every business rule SHALL record

- the domain variable it governs
- the file and line range of the condition
- the outcome when the condition holds, and when it does not

A rule without a named domain variable is not a business rule; it is a
description of code.

---

## Rule Count Is Not a Quality Measure

A unit with three real rules and forty null checks yields three rules.

Reporting forty-three is not more thorough. It is wrong.
